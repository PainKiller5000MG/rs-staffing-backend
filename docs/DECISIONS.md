## Decided

- 2026-11-16 · M2-SET · Settings choices made while building (not asked; easy to flip): (1) Every setting is one dated `pay_settings` row (key/value, company → client → site), validated against a key registry in `src/modules/settings/settings.keys.ts`; the salary engine reads them through `resolveSettings` (value + source). (2) Everything goes through maker-checker, including client-level pay period/cut-off; company-wide values are Admin only to propose and approve; client/site values use `sites.write` roles (Admin, Payroll, HR) and need a different approver. (3) "A change doesn't alter past months" = `effectiveFrom` cannot be before the first day of the current month, and must be after the newest approved value of that key (409 OVERLAP); the value it replaces ends the day before. There is no reject/cancel for a pending row yet (no hard deletes). (4) Pay period start, attendance due day and salary pay day are days 1..28 (the 28 cap avoids short months); the client row's `pay_period_start_day` is still the value until a dated row replaces it. (5) Weekly off = one or two weekdays or ROTATIONAL; per-site override is a SITE row. (6) PF/ESI/PT/LWF/bonus toggles and PF wage basis (CEILING|FULL) can be set at company or client level. (7) Default salary templates reuse `pay_settings` (key SALARY_TEMPLATE, or SALARY_TEMPLATE:<DESIGNATION>); a template must be active and either shared or the client's own. (8) Attendance layouts are immutable rows (DB trigger), one per version under a `layoutKey`; HQ Admin/Payroll/HR write, HQ reads; `attendance_imports.layout_id` is ready for M5 to fill. (9) M2-SET-09 (settings history, `asOf`) came free with the dated rows and is built. M2-SET-07 and 08 (P1) are not built. (Claude)
- 2026-11-16 · M2-SIT · Site API choices made while building (the user did not answer the questions, so the safe default was taken; all easy to flip): (1) `sites.code` stays globally UNIQUE, stricter than the story's "unique within the client" (relaxing a DB constraint needs sign-off); say if it should become UNIQUE(client_id, code). (2) Supervisor assignments reuse `user_site_scopes` with `is_primary`: pending until a second person approves (`/site-scopes/{id}/approve`); approving a primary ends the previous primary the day before the new one starts; the DB allows only one approved primary per site at a time. (3) "Internal employee with supervisor access" = active SUPERVISOR login whose employee is ACTIVE with staff type SUPERVISOR or HQ. (4) Site `address` stays NOT NULL (empty string = not given, returned as null). (5) The state lock after payroll (M2-SIT-03 AC1) is enforced in the service, not a DB trigger like the client code lock; "payroll has run" = a run line for the site in a run past DRAFT. (6) Create/edit/import/assign use `sites.write`; close is Admin only; `/sites/{id}/supervisors` is HQ only; `/me/sites` is supervisors only. (7) The site code and client never change after creation. (8) Zone stays a free code (M2 shortcut) with `sphere` CENTRAL|STATE; `minWageReady` is true when both are set, for the M7 payroll-run exception. P1 stories M2-SIT-09..11 not built. (Claude)
