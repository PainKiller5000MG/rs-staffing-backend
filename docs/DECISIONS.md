## Decided

- 2026-11-16 · M14-HOL · Holiday choices made while building (not asked; easy to flip): (1) The module's four open questions are not blockers for P0: state lists are data (entered or imported per state per year), clients add `CLIENT` days or swap a state day (`REPLACED`), and the P1 rules (optional days M14-OPT-01, weekly-off substitute M14-SUB-01) are not built. (2) Holidays are never hard-deleted: `removed_at/removed_by` hide a row, and the unique index (level, key, date, NULLS NOT DISTINCT) counts live rows only, so a removed day can be re-added and national days can't be duplicated. Removing a state holiday also removes its client replacements. (3) National days (26 Jan, 15 Aug, 2 Oct) are inserted for every year 2000..2100 by the migration, paid, fixed, not half-day, not editable to anything else (DB CHECK); years are limited to 2000..2100 in the API. (4) A client can replace only a `STATE` holiday (DB trigger), once, with a day in the same year; National can't be replaced. HQ (Admin/Payroll/HR) may still remove a national row to correct a mistake. (5) Writes use the `sites.write` roles (Admin, Payroll, HR); reads are all HQ incl. Auditor and Accounts; a supervisor reads only `GET /sites/{id}/holidays` for their own sites; employee access is M14-VW-01 (P1). (6) The merged list returns paid days only, one entry per date (levels shown), half-day flag kept; a half-day holiday counts as a working day in `isWorkingDay`. `ROTATIONAL` weekly offs have no fixed off weekday, so only holidays count there. `addWorkingDays` uses the weekly off in force on the start date. (7) Locked = a run with status `LOCKED` or `PUBLISHED` whose period covers the date and that has a line at an affected site (`REOPENED` is open). Affected sites = active sites of the level (national: all; state; client; site). Add, remove, pay-changing edit and client swap are all refused with 422 `MONTH_LOCKED`; a name-only edit is allowed. (8) Import takes JSON rows (like sites import) with `preview: true` to check without saving; a lower-case state code is normalised. (9) Site moving to another client mid-year (edge case) isn't modelled: a site's client never changes in this system. (Claude)
- 2026-11-16 · M2-SET · Settings choices made while building (not asked; easy to flip): (1) Every setting is one dated `pay_settings` row (key/value, company → client → site), validated against a key registry in `src/modules/settings/settings.keys.ts`; the salary engine reads them through `resolveSettings` (value + source). (2) Everything goes through maker-checker, including client-level pay period/cut-off; company-wide values are Admin only to propose and approve; client/site values use `sites.write` roles (Admin, Payroll, HR) and need a different approver. (3) "A change doesn't alter past months" = `effectiveFrom` cannot be before the first day of the current month, and must be after the newest approved value of that key (409 OVERLAP); the value it replaces ends the day before. There is no reject/cancel for a pending row yet (no hard deletes). (4) Pay period start, attendance due day and salary pay day are days 1..28 (the 28 cap avoids short months); the client row's `pay_period_start_day` is still the value until a dated row replaces it. (5) Weekly off = one or two weekdays or ROTATIONAL; per-site override is a SITE row. (6) PF/ESI/PT/LWF/bonus toggles and PF wage basis (CEILING|FULL) can be set at company or client level. (7) Default salary templates reuse `pay_settings` (key SALARY_TEMPLATE, or SALARY_TEMPLATE:<DESIGNATION>); a template must be active and either shared or the client's own. (8) Attendance layouts are immutable rows (DB trigger), one per version under a `layoutKey`; HQ Admin/Payroll/HR write, HQ reads; `attendance_imports.layout_id` is ready for M5 to fill. (9) M2-SET-09 (settings history, `asOf`) came free with the dated rows and is built. M2-SET-07 and 08 (P1) are not built. (Claude)

- 2026-11-16 · M3-BNK · Bank account choices made while building (none needed a user call): (1) **Every account, first or changed, is maker-checker**: HR/Payroll enters, verifies; only an Admin (`bank.approve`) approves, and never the entering user (the existing DB exclusion constraint already covers approved rows only). A pending account grants nothing. (2) Only one unapproved, non-failed account per employee at a time (`CHANGE_PENDING`); a FAILED one does not block a retry. (3) The name match compares the bank's returned name with the **employee's** name: word order, case, titles and one-letter slips are tolerated, an initial matches its name, extra words (joint account) cost points; below 80 = NAME_MISMATCH, which an Admin who did not enter the account accepts with a reason. (4) Approval sets `effective_from` = today, or the day after a LOCKED/PUBLISHED payroll run that covers today (M3-BNK-03 AC5; any client's run, deliberately conservative), and never on or before the previous account's own start (so a same-day replacement starts tomorrow); the old row gets `effective_to` = the day before. (5) Shared account (M3-BNK-06): checked on entry and again on approval against other non-exited employees' approved, still-open accounts via an HMAC of the number; only an Admin may override, with a reason, stored on the row. (6) `account_hmac` is nullable in the contract because no SQL backfill is possible; the service always sets it. (7) Payment mode CASH/UPI employees skip the "needs an approved bank account to go Active" rule (the cash question in M3 Open questions is still open). (8) No endpoint returns or reveals a full account number; `accountOn()` (payroll engine only) decrypts. (Claude)
